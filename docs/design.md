# Vouchkit 授权设计与审查

工作区由四个 Rust crate 组成。`0.1.0` 使用 Ed25519 和 `VK1-`。从 `0.2.0` 起可以使用 ECDSA P-256，并继续验证已有 `VK1-` 凭证。离线宿主只依赖 core。在线宿主使用相同的本地验证，再接入设备登记、租约续期和 CRL 分发。

## 发布前必须落实

| 设计风险 | 处理方式 | 验证依据 |
| --- | --- | --- |
| 委托者签发超期或越权租约 | 校验产品、签发窗口、等级、功能区间、设备公钥及含宽限期的总时长。签发时和消费时分别执行 | `wire::tests::a_valid_delegate_signature_cannot_exceed_certificate_limits` |
| 跨接口复用设备证明 | 将操作编号、规范化凭证摘要和激活参数纳入签名，SQLite 按购买和设备持久化已使用 nonce | core 设备证明测试，服务端 loopback 测试 |
| 并发申请最后一个席位 | 用 SQLite `BEGIN IMMEDIATE` 原子执行席位检查、登记和租约登记。数据库唯一键覆盖同一购买与设备公钥 | 服务端并发测试 |
| 激活响应推进客户端时间或扩大授权 | 响应时间必须与租约签名中的签发时间一致，并受本地时钟容差约束。初次激活和后续续租都核对保存的主密钥签名购买凭证。状态文件原子持久化 | 客户端租约/时钟测试 |
| 恢复旧 CRL | 客户端持久化最高验证序号，服务端在 SQLite 中保留签名文件并检查单调性。相同序号的冲突版本拒绝覆盖 | core CRL 测试，服务端和客户端集成测试 |
| CRL 与授权失陷窗口 | `since` 按租约签名里的 `issued_at` 比对。失陷的 DK 可以回填时间，租约总时长约束其可用窗口。时间不确定时，把 `since` 设为证书的 `not_before` | core 签发时间和部分吊销测试 |
| 购买凭证绕过在线授权 | `Entitlement` 仅产生 `NeedsActivation`。`VerifiedLicense` 只在完整本地验证后构造 | 固定向量与离线测试 |
| 软设备指纹被伪造或因升级而变化 | 以设备签名作为身份依据。保留提示字段供宿主诊断，硬件集成通过可失败的签名接口 | 设备证明及硬件适配器示例 |

## 运行边界

- 设备席位代表公钥。系统钥匙串改善私钥存放，支持 Ed25519 或 ECDSA P-256 的 TPM、HSM 和 USB 加密狗可提供不可导出的签名句柄。通过公钥和签名只能确认密钥持有；强制硬件来源需要额外的远程证明。
- 授权状态应使用每个产品单独的持久化文件。最大已见时间和 CRL 序号依赖持久化状态存续。恢复旧备份、丢失状态或长时间离线都会影响状态时效。
- 服务端实例共享同一 SQLite 数据库才共享席位、撤销和 nonce 状态。永久购买凭证缺乏经过签名的请求过期时间，nonce 记录随认证请求增长。后续协议可用服务端有界挑战缩短记录保留期。
- 一个购买 ID 在服务端对应一份作者签名的购买凭证。更新产品授权时签发新 ID，并按业务需要吊销旧 ID。服务端把离线授权与购买凭证的权限投影到受委托租约。
- CRL 序号对同一发布者的受信主钥集合单调递增。轮换期间将新旧公钥部署到客户端、服务器和作者台账工具。备份台账与相邻的 CRL 文件。
- Crockford Base32 容忍大小写、空白、分隔符，以及 `O/0`、`I/L/1`。这些写法代表相同的签名字节。验收以篡改解码后字节为准。

## 数据库决策

按 DDIA 的事务、存储与 schema 演进原则，在线授权引擎通过 `ActivationStore` 使用事务存储。同一部署内的实例共享同一权威存储。后端需要提供一致读快照、可串行化写入、写后可读和原子提交，且每次执行只调用一次事务回调。SQLite 参考后端采用 WAL、`synchronous=FULL` 和 `BEGIN IMMEDIATE`，在读取席位数之前获取写入权。这样两个实例同时申请最后一个席位时，后到的事务读取的是先前已提交的席位数。

| 数据 | 约束与生命周期 |
| --- | --- |
| `entitlements` | 购买 ID 为主键，保存作者签名的原始凭证供续租重新认证 |
| `activations` | 按购买和公钥唯一，部分索引只覆盖有效席位，停用保留登记历史 |
| `issued_leases` | 租约 ID 唯一并关联设备登记，停用时删除续租资格，签发时清理该设备已过宽限期的记录 |
| `request_nonces` | 按购买、公钥与 nonce 唯一。业务拒绝消耗已认证 nonce，临时签名或存储故障允许重试 |
| `server_state` | 同一个事务提交签名 CRL 与其序号，最高时钟与请求状态一并持久化 |

通过 `PRAGMA user_version` 识别 schema。初始化和迁移在写事务中执行，遇到未知版本停止启动。从 schema 1 到 schema 2 的原子迁移把允许的设备公钥长度扩展到 32 字节 Ed25519 和 33 字节压缩 SEC1 P-256，保留相同的 Ed25519 字节以及原席位、签发租约和 nonce 记录。备份时使用 SQLite backup API，恢复后先装入可获得的最新签名 CRL，再开放流量。

## 首版 wire format

所有版本 1 信封先写版本号 `1` 和类型 `1`（license）、`2`（CRL）、`3`（certificate）。所有签名都是 Ed25519，验签输入为含 NUL 结尾的域字符串和原始信封（从版本号到载荷末尾）。信封末尾为 64 字节签名。Postcard 载荷按公开 Rust 结构体的字段顺序编码。固定长度整数使用原始单字节或 Postcard varint，信封长度字段使用大端。

- License 域为 `vouchkit-license-v1\0`。版本与类型后为签发者（`0` 主钥、`1` 委托）和主公钥 ID。委托信封随后包含 `u16` 证书长度与已签证书。之后为 `u16` 载荷长度和载荷。载荷上限 768 字节，证书上限 256 字节。
- Certificate 域为 `vouchkit-delegation-v1\0`。类型后为主公钥 ID、`u16` 载荷长度及证书载荷。
- CRL 域为 `vouchkit-crl-v1\0`。类型后为主公钥 ID、`u32` 载荷长度及 CRL 载荷。首个有效序号大于零，最多 8192 个条目。
- 证明域为 `vouchkit-activate-v1\0`。后接 16 字节 nonce、16 字节购买 ID、32 字节设备公钥、单字节操作编号（激活 1、续租 2、租约停用 3、购买凭证停用 4），以及 32 字节的原始信封 BLAKE3 摘要。激活另签入三个大端 `u16` 版本组件、提示存在位和可选 16 字节提示。
- 设备本地验证域为 `vouchkit-device-v1\0`。后接 16 字节授权 ID 和 16 字节本地随机挑战。
- JSON 二进制字段使用无填充 Base64URL。公钥文件使用标准 Base64。详细样例见 [固定向量](../testdata)。

## 多算法信封与兼容性

版本 2 延续首版字段顺序，在每个信封的主公钥 ID 后增加一个签名算法字节，`0` 为 Ed25519，`1` 为 ECDSA P-256。签名域的版本后缀改为 `-v2\0`。签名范围包含版本、算法标识、长度、内嵌证书和载荷。主公钥 ID 对应的受信算法必须与信封一致，委托签名必须与受信证书中的算法一致。旧格式的签名规则和编码保持兼容。

- P-256 公钥为 33 字节压缩 SEC1 点，签名为两个各 32 字节的大端标量 `r || s`。使用 SHA-256，验签拒绝高 S、无效点、算法不匹配与未知算法。
- 版本 2 的设备公钥和委托公钥在 Postcard 中有显式算法标识。激活证明在凭证为版本 2 或设备为 P-256 时使用 `vouchkit-activate-v2\0` 并在设备公钥前签入算法标识。P-256 本地设备证明使用独立的 `vouchkit-device-v2\0` 域，且签入算法和设备公钥。旧 Ed25519 验证器只能消费 Ed25519 版凭证和租约。
- 版本 1 和版本 2 的 CRL 共享同一发布者序号。轮换算法时向应用及服务端分发新旧公钥，并继续递增序号。
- `SigningProvider`、`DeviceProver`、`Transport` 和 `ActivationStore` 支持宿主在运行时提供实现。签名 provider 可在内置算法下使用 HSM、KMS 或其他密钥管理方式。新增 wire 算法需要定义经过签名的标识、规范编码与互操作向量。
- `FeatureSlots` 提供 65536 个稳定 ID。范围覆盖模块、子功能和未来保留区间。证书与租约都采用规范化区间，并检查每项租约授权都在证书范围内。签发之后应保留槽位原语义。
